# 售后返修承诺：三套改造组合与推荐底稿

这是 2026-10-02 独立技能使用试验的实际答复。输入只有现题描述和材料名称，用于检查新方法能否形成具体改造方案。

建议优先采用第二套：把“逐单可修、逐单报价”改为“这批工单能否共同兑现，以及据此能向客户报什么价、承诺什么日期”。它能直接利用现有材料中的备件流水、两库转移、台位日历和既有交期。第一套更偏返修范围与费用责任，第三套更偏变更后的承诺修订，三者不要一次全部叠上去。

以下是基于材料名称的设计建议，尚未查看原件、核验可解性或试测模型。文中“保留某类记录”均以原件确实存在为前提；不声称已经发现重号、冲销、在途差异或违规承诺。

## 先撤掉现有题目中的代劳

现有总表的“剩余保修、备件可用数、应套用规则、报价”正好把判断链压成了查表。这四列不能继续作为作者算好的当前事实发给模型，应留在作者区用于核对，并从可追溯原件恢复它们的依据。

若某列本来就是业务系统的原始快照，或报价已经获得客户批准，不应为了加难删掉事实。保留其真实形成时间、用途、状态和引用关系；不再把这项已知结果的恢复算成考点。作者整理的总表与真实业务快照须分清。

原始工单中的客户诉求、故障表现、已发生的操作、真实标识等继续保留。不要把整张表随机拆成多个文件，也不要把所有标题改成模糊名称。

## 三套不同的改造组合

### 组合一：先确定本次到底修什么，再决定谁承担哪些费用

**核心改变：**保留“返修判断与报价”的原目标，把计价对象从清洗好的工单行改为有依据的本次维修范围。

**附件怎样改：**工单保留原有设备标识；资产别名按真实客户、有效期间和序列号等连接依据保留；拆机与换件记录保持设备、部件和事件各自粒度；基础保修/收费条款与部分修订按来源保存。若实际存在同一设备多张单、部件已更换、既往故障与本次故障不同等情况，保留其关系，不先写成“同一返修/新故障/重复记录”标签。

**规则怎样组合：**本次对象及维修范围，决定哪些保修或收费条款适用；局部修订只改变它实际覆盖的项目。是否存在返修保障期、部件单独保修、重复维修免人工、收费抵扣顺序，必须由原件确认，不能把这些常见说法当作已有条款。

**判断怎样改变执行：**一次对象或维修范围判断，必须改变某个真实的拆检/更换项目、备件需求或工时，再改变报价明细和维修任务。比如，原件若能证明两张单对应同一次尚未结束的维修，其处理应影响重复计费或重复领料；只让模型找出“疑似重复”而后续照旧，不算改造成功。

**适合检验的错误：**把同别名的两台资产合并、把已换下部件的状态套给当前部件、将某项费用豁免扩大成整单免费。是否真有这些错误机会，要在原件中核实。

**必须补齐：**完整基础规则、计价依据、对象连接锚点，以及故障/检验记录和获准维修方案之间的依据。仅有换件历史不能证明本次技术上可修。

### 组合二：每单看似可修，整批能否同时兑现——推荐

**核心改变：**原题把“有备件”和“有空台位”当作逐单标签；新题交付一套整批共同成立的维修、报价与交期安排。

**附件怎样改：**提供有起点的原始备件流水，保留真实库别、料号、数量、状态与时点；两库转移保留关联单据和实际执行状态；台位日历保留已有占用及可工作窗口；工单与拆机资料支持具体维修需求；既有客户回复保留形成时点、适用工单及批准状态。不得先给“每单可用库存”和“最早完工日”。

**规则怎样组合：**同一维修方案同时受用料资格、资源可用时点、台位适配与作业约束、承诺调整权限影响。两库总量够，并不能直接推出某工单在某地点、某时间可以开工；所有工单分别有可选台位，也不等于它们能同时使用同一时段。

**判断怎样改变执行：**

`维修范围判断 → 料号/数量与作业需求 → 可同时执行的用料与台位安排 → 完工日期 → 客户承诺与对应报价`

这条链写在作者记录中，不写成模型操作步骤。若某笔转移对当前可用量的解释改变，必须能观察到某个工单改用资源、调整开工/完工时点或保留条件；若所有安排都不变，这笔差异就不是核心难点。报价由最终维修范围、用料与适用计价规则生成。只有原件确有“报价获批后才能开工”等规定时，才把费用批准接成排程前置条件。

**为什么推荐：**现有材料名称已经覆盖了两个会竞争的资源系统和既有客户承诺。难点可以落在一套真正要拿去执行的安排上，而不必另加长报告。正常脚本可以批量恢复和求解，仍需保证选取的事实、组合约束及输出相互一致。

**必须补齐：**库存期初或可靠基准、状态与可用性的定义、已有占用是否完整、维修用料和作业工时、台位适配与前后置约束、必要的转移时效、完整计价规则、交期含义与调整权限。日历本身不包含每项维修要占用多久，流水本身也不一定包含可用余额。

### 组合三：局部规则或事实变化后，修订已答复的承诺

**核心改变：**从新做一遍判断，转为对真实基线负责：哪些已答复事项仍成立，哪些必须变更，变更后怎样共同执行。

**附件怎样改：**保留真实已批准的报价/维修安排和客户回复作为基线，再保留有对象、范围、生效依据的规则修订及相关事件。一次提供完整冻结历史即可，不必等模型作答后临时加条件。实际存在事件发生时间与补录时间差异时，保留两种时间的含义。

**规则怎样组合：**某修订可能仅覆盖特定对象、费用项或状态；受影响的范围变化后，原用料/台位占用可能需要重排，进而影响其他本来不受条款直接覆盖的工单。直接适用范围与间接资源影响范围需分别有依据。

**判断怎样改变执行：**有效变更判断决定哪些报价行、资源安排、客户交期需要更新；修订后的共享资源分配又必须能成立。交付当前可执行版本，并标明实际需要调整的客户承诺。不能只把旧结论改一句“按新规处理”。

**区别与限制：**这套主要检验影响范围和变更传播，不要求模型重新猜所有历史结论。只有“已答复交期”还不足以做最小修改题；还需基线报价、资源占用或已批准方案。若要求“最小改动”，须公开比较口径与允许调整范围；否则接受有依据的合理修订，不暗定作者唯一安排。

**必须补齐：**基线及其批准状态、完整规则继承关系、各时间字段含义、可调整与不可调整事项。拿不到可连接的真实基线，就先不采用这套。

## 推荐方案的附件组织

这是打包方案，不是声称已经生成了下列业务附件。文件按真实来源组织，优先保留原格式；不为增加文件数拆分，也不把作者的正确连接表交给模型。

| 模型输入中的材料组 | 保留内容与必要连接 | 发布前检查 |
|---|---|---|
| 中性目录与导出说明 | 原始文件名、来源、形成/导出时间、覆盖对象与时间、字段单位和时间语义 | 不写“这里解决库存重复”“此规则最终有效”等答案导航；导出范围不能由模型猜 |
| 工单原始导出 | 任务范围、工单号、原资产标识、客户诉求、故障及当前进度等真实字段 | 区分待处理清单与历史上下文；原作者推导列另存作者区 |
| 客户资产别名资料 | 原别名及能够确定实体和有效范围的记录 | 不人为制造无法区分的同名；局部歧义须能隔离到具体工单 |
| 拆机、换件及必要的检验/工艺记录 | 已发生事件、对应设备/部件、执行时点、维修项目依据 | 必需项目、用料、工时、台位适配能从输入恢复；缺失部分要补原依据 |
| 备件基础记录与出入库流水 | 可靠期初/基准、原始交易标识、料号、库别、数量、状态、时点及真实冲回关系 | 区分库存事实、已有占用与本次拟分配；同时能核对局部及整体数量 |
| 两库转移单与必要执行记录 | 与流水可连接的转移标识、起讫库、数量和已有执行状态 | 在途、签收、可使用时点按真实业务定义；不得预先假定单据日期等于可用日期 |
| 服务与计价依据 | 完整基础条款、修订原文、签发/生效/适用范围；零件价、人工费及适用口径 | “部分规则变更”不能替代基础规则；避免只给结论性的适用规则总表 |
| 台位日历及作业参数 | 实际工作时段、已有占用、维修适配、必要持续时间与先后关系 | 明确可否拆分、跨班、并行、加班；只保留与实际业务有关的约束 |
| 客户交期回复与承诺管理资料 | 工单连接、原交期、回复/批准状态、承诺含义及允许调整范围 | 区分完工、出库、到货等日期；已回复不能自动当作已预留资源 |

模型输入区只放题面与业务资料。作者区另存：原整理总表、源位置与连接核对、各规则组合的预期结果、可接受替代安排、评分依据。不要把这些内容放在隐藏工作表、批注或文件元数据中随包发出。

推荐把模型交付压成一个工作簿，只有两类必要内容：客服要用的工单承诺/费用明细，车间和仓库要用的执行安排。证据与核验结果可以随对应记录提供，无需另写泛泛的管理报告。

## 模型题面底稿

独立可复制版本见 [模型题面底稿](repair-commitment-prompt.md)。其中两个时间占位必须换成真实委托值；正文所依赖的业务规则也必须先补进输入。

本底稿采用“按资料中已明确的权限与优先要求形成可执行方案”的口径，不暗设全局最优。若业务没有既定优先级，作者应在出题前明确委托的取舍目标；可以接受多套满足该目标和约束的方案，不用作者偏好的工单排序判错。

## 原件到位后的最小验证

先从实际资料选一小组能够形成共享资源竞争、且证据闭合的工单，不先扩大行数。作者独立完成以下检查：

1. 能恢复至少一套符合输入依据的维修范围、报价与联合执行安排；确实无法承诺的局部项有明确原因，正常项能够继续。
2. “直接沿用总表”“忽略库别或可用时点”“逐单重复占用同一资源”这些便捷做法中，至少一种在具体结果上产生可核验错误。没有实际反例，就不宣称该机制有效。
3. 改变一个有原件支持的上游判断时，记录哪些用料、工时、费用或交期随之变化。只改变解释文字的连接应删除。
4. 数量、时段与最终承诺可以回代核对；替代可行安排被公平接受。高效脚本一次求解成功也应得分。
